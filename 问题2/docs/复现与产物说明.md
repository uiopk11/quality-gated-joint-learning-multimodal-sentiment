## 1. 环境与入口

命令在 `problem2_solution/` 内执行。历史实测环境为 Windows x64、Python 3.12.14、PyTorch 2.8.0+cu128、transformers 4.44.2、NumPy 1.26.4。固定依赖见 [requirements.txt](../requirements.txt)、[requirements-lock.txt](../requirements-lock.txt)，PyTorch 来源见[来源清单](../reproducibility/environment/torch_source_manifest.json)。基础 BERT 从包内离线加载。

换机器时在包外创建环境；下面安装命令对应 Windows/Python 3.12，需要下载依赖。不同平台需适配，不能直接复制原虚拟环境或保证同 seed 跨设备逐位一致。

```powershell
python -m venv ..\problem2_env
..\problem2_env\Scripts\python.exe -m pip install -r requirements.txt
..\problem2_env\Scripts\python.exe -m pip install -r requirements-lock.txt
..\problem2_env\Scripts\Activate.ps1
python -X utf8 run.py verify --checkpoints
```

本机已有开发解释器在包外 `../workbench/problem2/tmp/environment/Scripts/python.exe`，不属于交付依赖。代码运行以工程所在位置解析资源，不依赖个人缓存或原工作区的数据目录。

当前实验显式使用 `--version four-models`。省略版本仍会进入旧 `multitask`。旧 `baseline`、`standardized`、`missing`、`missing-standardized`、`missing-only`、`multitask` 和 `legacy` 接口仅为历史复现保留，编号含义与当前 M0–M3 不通用。各自限制以对应 `--help` 为准。

M1/M3 使用 [four_models_v1.json](../configs/four_models_v1.json)；新 M0/M2 配置从旧标准化回归流程派生，不能传入该 Accuracy 配置。`configs/evaluation.json` 是旧回归阈值配置，`outputs/<run>/evaluation.json` 是结果报告，两者作用不同。

## 2. 查看、整理与检查

```powershell
# 只读查看当前训练目录
python -X utf8 run.py report --all
python -X utf8 run.py report --run-name fm_v1_m3_s1111 --full

# 展开历史版本或独立评价；JSON 适用于程序读取
python -X utf8 run.py report --all --include-history
python -X utf8 run.py report --all --include-evaluations
python -X utf8 run.py report --all --json

# 读取已保存记录，整理预测、图表、摘要；不运行模型
python -X utf8 run.py report --all --organize

# 只读检查资源、冻结绑定与已有权重来源
python -X utf8 run.py verify --checkpoints
```

新 `train/evaluate` 命令结束会自动整理本次写入的记录。`report --all` 的历史显示开关只影响展示；`--all --organize` 仍处理历史和独立评价。整理不会重新选模、校准阈值、推理或替换指标，也不能补出尚未运行的实验。旧 `--write-summary` 仍兼容，通常无需单独使用。

可捕获的错误/中断会记录真实状态；强制杀进程后不能保证收尾，可再整理已落盘文件。未知原因保留未知。记录耗时是整个命令的墙钟时间，含导入和准备阶段。

## 3. 一个训练目录怎样读

```text
outputs/<run_id>/
  best.pt                      原最佳权重
  training.json                训练摘要：协议、预算、最佳轮次和结束状态
  evaluation.json              结果入口：valid/test、缺失面板、来源与产物
  config.json                  原生效配置
  history.json                 原逐轮记录（部分历史版本没有）
  preprocessing.json           原标准化参数
  provenance.json              原来源与数据绑定
  predictions/<split>/         按条件整理的原预测 CSV
  predictions/<split>/<eval_id>/ 独立评价关联来的原预测 CSV
  analysis/
    report.md                  该次运行的分析入口
    figures/                   已有指标生成的 SVG
    error_cases.csv            已有预测生成的错误案例
  details/                     原日志、条件 JSON/CSV、decision、原件快照
  evaluations/<eval_id>/       同一权重的独立评价，不是新一轮训练
```

日常看两份 JSON 和 `analysis/report.md` 即可。根目录的 `config/history/preprocessing/provenance` 是运行和复现所需的原记录，不是多余摘要；老版本未保存的文件不会补造。条件细节统一放 `details/`。独立评价目录仅保留其配置、结果及原件，分析集中到对应训练目录；原条件 JSON/CSV 仍保留，不复制权重。

`training.json` 不是断点续训文件。最佳权重没有保存的优化器状态、历史时间等信息不能从摘要恢复。`evaluation.json` 的八个主要分区如下：

| 分区 | 内容 |
|---|---|
| `valid` / `test` | 相应划分已保存的 clean、mixed 指标与来源 |
| `robustness` | 配对面板及各自共同样本数、条件、预测引用 |
| `ablation` | 报告器支持的同协议对照引用；不等于全部论文消融已完成 |
| `attachment3` | 无标签专项预测的状态、覆盖与文件；未执行保持 `not_run` |
| `diagnostics` | 混淆矩阵、逐类指标与误差统计引用 |
| `protocol` | 模型/评价版本、类别与决策规则、数据身份 |
| `artifacts` | 权重、预测、图表、分析及原件清单 |

`reporting_schema_version=2` 只表示展示格式。`completed`、`partial`、`not_run` 和未知状态依证据记录，不以 0 代替未运行。附件三没有真值，`metrics=null`、`scoring_status=not_applicable_unlabeled`，不可拿附件二分数填入。

`_reporting.condition_sources` 可定位权威原件及 JSON pointer；`details/reporting_originals/` 和 `reporting_manifest.json` 保存原 JSON、哈希及路径对应。相同条件出现不同结果时保留冲突，不自动挑最高分或最新分。原始兼容字段有的保留内联，有的由 `legacy_fields_refs` 引用；代码通过 `read_original_evaluation` 校验后读取。

面板指标只能使用该面板共同 cohort；条件级 CSV 可能有更多样本。图表不重算正式指标，错误案例沿用原预测类别与强度；旧 CSV 没有类别时不套新阈值制造分类结果。每个条件分别统计分母，同一样本的多个视图不是新增独立样本。

## 4. 比较报告的能力边界

`outputs/comparisons/` 中的自动对照目前只配对同为 `four_models_accuracy_v1` 的同 seed、同数据绑定记录，即既有 Accuracy 版 M0/M1、M2/M3。同方法多个候选或条件冲突会明确提示，不自动择优。

恢复后的 MAE M0/M2 与 M1/M3 属于不同原生协议，**当前自动 comparison 不会替你生成这组主比较**。论文主表应按[实验指南](实验指南.md)指定的 run、split、condition、N、权重和来源汇总，披露协议差异；不能把旧自动对照表换个标题就当作新的 MAE 基线比较。跨协议主表的汇总仍是待办，所需数据缺项先实际补评。

## 5. 冻结数据与来源保护

当前包内保留了冻结 `resources/missing_data/mix_v1/`、基础模型 `resources/pretrained/`、作者代码及许可证 `resources/third_party/`，但 `resources/data/` 为空，附件二 `resources/data/attachment2/` 和附件三 `resources/data/attachment3/aligned/` 并未随包落地。重新评价或附件三推断前，必须从正式数据源补齐输入并按 `reproducibility/` 中的清单、审计和数据绑定核验；不能修改清单来迁就错误文件。日常无需重建已经冻结的缺失掩码。

`run.py verify` 只读检查；`data refresh-acceptance` 会写验收文件，不能拿它代替检查或修复指纹错误。如确需构造新版本，`data build --output <尚不存在的新目录>`，不要覆盖当前 mask、manifest、acceptance、metadata 或统计。具体规则见[数据协议](数据构造协议.md)。

`reproducibility/` 保存原始代码、路径映射、环境、历史审计与逐版兼容证据。历史路径是来源说明，不代表还依赖旧外部目录。旧权重保持原字节，兼容层仍验证实际源码、数据和绑定，不允许伪造旧哈希或直接修改 checkpoint 身份。开发脚本/测试在包外 `workbench/problem2/`，不属于正式运行依赖。根目录仅保留 `run.py` 入口，不在包内新建虚拟环境或旧入口脚本。

2026-09-26 将重复计划、运行说明、旧结果审计和一次性目录验收从日常 `docs/` 合并移除，保留实验指南、数据协议和本文。旧文档原字节集中在 `reproducibility/docs_consolidation_revision/prior_source/` 作为受指纹保护的历史证据，不再作为现行操作说明；无需逐份阅读。每个 run 的 `analysis/report.md`、上游 README/许可证及冻结数据验收报告仍有各自用途，未当作冗余说明删除。
